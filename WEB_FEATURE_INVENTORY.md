### B) Every stat/number and its exact calculation

**Status derivation** (single source of truth, used everywhere) — `lib/utils/index.ts`, function `getEffectiveStatus`:
```ts
/**
 * Derives the real trip status from dates, overriding the stored DB value for
 * date-determinable states. "cancelled" is always manual and never overridden.
 * Without a start_date the stored status is returned as-is.
 *
 * Rules (all comparisons at day granularity, local time):
 *   start_date > today          → 'upcoming'
 *   start_date ≤ today
 *     AND (end_date ≥ today OR no end_date)  → 'active'
 *   end_date < today            → 'completed'
 */
export function getEffectiveStatus(
  trip: { status: string; start_date?: string | null; end_date?: string | null },
): string {
  if (trip.status === 'cancelled') return 'cancelled'
  if (!trip.start_date) return trip.status

  const today = startOfDay(new Date())
  const startDay = startOfDay(parseISO(trip.start_date))
  const endDay = trip.end_date ? startOfDay(parseISO(trip.end_date)) : null

  if (isAfter(startDay, today)) return 'upcoming'
  if (endDay && isBefore(endDay, today)) return 'completed'
  return 'active'
}
```

### C) Every interactive control — filters, search, sort, status logic (quoted verbatim)

#### Search
```js
const matchesSearch =
  t.name.toLowerCase().includes(search.toLowerCase()) ||
  t.country.toLowerCase().includes(search.toLowerCase())
```
Plain-text `Input`, case-insensitive substring match against trip **name** OR **country** only (not city, not notes). Updates `search` state on every keystroke, fully client-side, no debounce, no API call.

#### Status filter — the two-dimensional planning model

Dropdown options, exact list:
```js
const STATUS_FILTERS: { value: string; label: string }[] = [
  { value: 'all', label: 'All Trips' },
  { value: 'planning', label: 'Planning' },
  { value: 'upcoming', label: 'Upcoming' },
  { value: 'active', label: 'Active' },
  { value: 'completed', label: 'Completed' },
  { value: 'cancelled', label: 'Cancelled' },
]
```

Matching logic, quoted verbatim:
```js
let matchesStatus: boolean
if (statusFilter === 'all') {
  matchesStatus = true
} else if (statusFilter === 'planning') {
  // Planning is a separate dimension — true while is_planning flag is set,
  // but only relevant for upcoming trips (active/completed trips are past the planning phase)
  matchesStatus = (t.is_planning ?? true) && !['cancelled', 'active', 'completed'].includes(getEffectiveStatus(t))
} else if (statusFilter === 'cancelled') {
  matchesStatus = getEffectiveStatus(t) === 'cancelled'
} else {
  // 'upcoming' | 'active' | 'completed' — purely date-derived
  matchesStatus = getEffectiveStatus(t) === statusFilter
}
```

This is the two-dimensional model:
- **Dimension 1 — date-derived lifecycle** (`getEffectiveStatus`, quoted in full under §1B): `cancelled` always wins and is a manual, DB-stored flag — never overridden by dates. If `start_date` is missing, the raw stored `status` column is returned unchanged. Otherwise: `start_date` in the future → `upcoming`; `start_date` today-or-past AND (`end_date` today-or-future, or no `end_date`) → `active`; `end_date` in the past → `completed`.
- **Dimension 2 — planning flag** (`trip.is_planning: boolean`, a separate DB column on `Trip`, default-true if null via `?? true`). This is an *independent* boolean orthogonal to the date lifecycle — it does not get computed or overridden by `getEffectiveStatus`.

The **"Planning"** filter option selects trips where: `is_planning` is truthy (or unset) **AND** the trip's effective status is NOT `cancelled`, `active`, or `completed` — i.e. "still-in-planning, not-yet-started, not-cancelled" trips (mostly overlaps with `upcoming`/dateless `planning`-status trips, but is distinct from the `'upcoming'` option because it additionally requires `is_planning` to be true).

The **"Upcoming"**, **"Active"**, **"Completed"** filter options are purely date-derived: `matchesStatus = getEffectiveStatus(t) === statusFilter`, completely ignoring `is_planning`.

The **"Cancelled"** filter option: `matchesStatus = getEffectiveStatus(t) === 'cancelled'` (equivalent to raw `t.status === 'cancelled'` since cancelled is never derived from dates).

Selecting an option sets `statusFilter` state; combined with `search` via logical AND (`matchesSearch && matchesStatus`) to produce `filtered`.

#### Sort
No user-facing sort control — a **fixed** sort is always applied after filtering, quoted verbatim:
```js
// Sort: trips with a start_date ascending (soonest first), no-date trips last by created_at desc
const sorted = [...filtered].sort((a, b) => {
  if (a.start_date && b.start_date) {
    return new Date(a.start_date).getTime() - new Date(b.start_date).getTime()
  }
  if (a.start_date) return -1
  if (b.start_date) return 1
  return new Date(b.created_at).getTime() - new Date(a.created_at).getTime()
})
```
i.e. trips with dates sort earliest-date-first across all trips regardless of past/future (not "upcoming-first"). Trips with no `start_date` are always pushed to the bottom, ordered by `created_at` descending (newest-created first) among themselves.

### D) External links / integrations — GOOGLE MAPS (flagged item)

**Exact URL-building function**:
```ts
function getMapsUrl(item: ItineraryItem): string | null {
  if (item.google_maps_url) return item.google_maps_url
  if (item.latitude && item.longitude) return `https://www.google.com/maps?q=${item.latitude},${item.longitude}`
  if (item.location_name) return `https://www.google.com/maps/search/${encodeURIComponent(item.location_name)}`
  return null
}
```
Priority order, exactly as coded:
1. **Stored field** `item.google_maps_url` — used verbatim if present. Populated when the user picks a place via `PlacesAutocomplete` (`p.googleMapsLink`) or when an activity is added from the TripAdvisor Suggestions panel (`s.google_maps_url`).
2. **Fallback — lat/lng construction**: `https://www.google.com/maps?q=${item.latitude},${item.longitude}` (note: `?q=lat,lng`, NOT the `search/?api=1&query=` format).
3. **Fallback — name-only text search**: `https://www.google.com/maps/search/${encodeURIComponent(item.location_name)}` (path-encoded search term, no `?api=1`).
4. Returns `null` if none of the three are available — no Maps link/button renders at all.

Notably, this function does **not** use `google_place_id` even though that field exists on the `ItineraryItem` type and is captured into the form during Add/Edit — the `place_id:...` URL format (`https://www.google.com/maps/place/?q=place_id:...`) is never used anywhere in this file.

```js
const totalPlanned = items.reduce((s, i) => s + i.planned_amount, 0)
const totalSpent   = items.reduce((s, i) => s + i.actual_amount, 0)
const tripBudget   = localBudget || totalPlanned      // falls back to sum of planned if no budget set
const remaining    = tripBudget - totalSpent
const isOverBudget = remaining < 0
const overallPct   = tripBudget > 0 ? Math.min(100, Math.round((totalSpent / tripBudget) * 100)) : 0
```
Per-category (`byCategory`):
```js
const catItems = items.filter(i => i.category === cat)
const planned  = catItems.reduce((s, i) => s + i.planned_amount, 0)
const actual   = catItems.reduce((s, i) => s + i.actual_amount, 0)
```
Per-category card percentage: `pct = planned > 0 ? Math.round((actual / planned) * 100) : (actual > 0 ? 100 : 0)`; `over = actual > planned && planned > 0`; `diff = planned - actual`.
Per-row "isOver" flag: `item.actual_amount > item.planned_amount && item.planned_amount > 0`.

### B) Stats and exact calculations

**Visited Countries page:**
- `visitedCount = visited.size` — size of the Map built from `visited_countries` table rows for the user.
- `visitedRegionsCount = visitedRegions.size` — size of the Map from `visited_regions` rows.
- `partialCountries` (Set) — countries that have visited-region rows but no full-country row:
  ```js
  for (const key of visitedRegions.keys()) {
    const countryCode = key.split(':')[0]
    if (!visited.has(countryCode)) partial.add(countryCode)
  }
  ```
- `continentsVisited` — distinct continents from fully-visited countries plus continents of partially-visited countries.
- `progressPct = Math.round((visitedCount / TOTAL_COUNTRIES) * 100)` — TOTAL_COUNTRIES = 197.
- `nextAchievement = ACHIEVEMENTS.find(a => visitedCount < a.threshold)`.
- `continentCounts` — per-continent `{ total, visited }` where `visited` counts countries that are either fully or partially visited, `total` = all countries in `COUNTRIES` for that continent.
- Per-country region progress: `regionProgress(code)` returns `{ done, total }` where `done = sr.regions.filter(r => visitedRegions.has(...)).length`, `total = sr.regions.length`; percentage shown as `Math.round((progress.done / progress.total) * 100)`.

**Dashboard `WorldMapWidget`:**
- `stats.visited = visitedCodes.size` where `visitedCodes = new Set([...tripVisitedCodes, ...manuallyVisited])`.
  - `tripVisitedCodes`: countries from trips where `getEffectiveStatus(t) === 'completed'`, resolved to ISO2 via `resolveA2(t.country_code, t.country)`.
  - `manuallyVisited`: from the `visitedCountryCodes` prop (i.e. the `visited_countries` table).
- `stats.planned = plannedCodes.size` — countries from trips with `status` in `['upcoming','planning','active']` OR `start_date >= now`:
  ```js
  new Set(
    trips
      .filter(t => ['upcoming','planning','active'].includes(t.status) || (t.start_date && new Date(t.start_date) >= new Date()))
      .map(t => resolveA2(t.country_code, t.country))
      .filter(Boolean)
  )
  ```
  Note this filter uses raw `t.status` OR a future start date — a **third, distinct** status-derivation path from `getEffectiveStatus`.
- `stats.continentsVisited = countContinents(new Set([...visitedCodes, ...partiallyCodes]))` — uses the hardcoded `CONTINENT` ISO2 lookup table.
- `stats.upcomingCount = orderedUpcoming.length` — trips with a future `start_date`, sorted, capped to 6.
- `partiallyCodes` — `Object.keys(partiallyVisitedRegions)` minus anything already in `visitedCodes`.
- Header subtitle line: `"{visited} countries visited • {upcoming} upcoming trips • {continentsVisited} continents explored"`.

### Cross-cutting notes for the mobile dev (Settings)

- **Persistence pattern is uniform**: every sub-section (except Subscription, which is non-functional, and the Account page's avatar/password fields, which use Supabase Auth instead of `user_settings`) does a client-side Supabase `upsert` on `user_settings` keyed by `onConflict: 'user_id'`, only on an explicit "Save" tap — no per-field auto-save/debounce anywhere except the Theme picker, which also applies live via `next-themes` before saving.
- **Toast library**: `sonner`, used identically across all sub-sections for success/error feedback.
- All Save buttons render a `Loader2` spinning icon while their local saving boolean is true, and are `disabled` during that window.
- Mobile save buttons are always a `fixed bottom-0` bar; desktop save buttons are always inline, right-aligned at the bottom of the card stack — this pattern repeats identically across Account, Appearance, Language, Notifications, Privacy.
- No sub-section other than Account's avatar path touches Supabase Storage; no sub-section touches any payment/billing provider (Subscription page is fully static/dead UI).
